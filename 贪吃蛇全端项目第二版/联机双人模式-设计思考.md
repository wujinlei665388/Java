## 1. 现状盘点：联机能白捡什么

先把现有代码里"天生适合联机"和"天生阻碍联机"的部分分清楚。

### 1.1 可以直接复用的（好消息）

| 现有东西 | 位置 | 为什么好复用 |
|---|---|---|
| `drawSnake(ctx, v, snake, dir, CELL, frame)` | `game/render.js` | **蛇是入参**，不是全局变量 → 画第二条蛇基本是"再调一遍"，换个 theme 就是对手 |
| 皮肤系统 `SKINS` / `resolveTheme(map, skin)` | `game/skins.js` | 双方**各选各的皮肤**几乎免费：两人用同一个地图 theme，但各套自己的 skin |
| 地图系统 `MAPS` / `wallSet(map)` | `game/maps.js` | 联机只需同步一个 `mapId`（字符串），墙体两端各自算，不用传地图数据 |
| 回放编码 `encodeTrack()` | `game/replay.js` | 将来做"双蛇回放"可直接编码两条轨迹，不必新格式 |
| 统一响应 `Result` / 前端 `request.js` | 后端/前端 | 房间的 HTTP 接口（创建/加入）直接沿用同一套规范 |
| 内存态即可 | —— | 这台机器**每次开机重置**，房间本来就不该指望持久化 → 内存房间表反而是最合理的设计 |

**最关键的复用点**：渲染层已经参数化，所以"画出两条蛇"几乎是零成本。真正的成本全在**游戏状态的组织方式**上。

### 1.2 必须改的（阻碍）

```js
// Game.vue 现状（第 197~213 行附近）
const SIZE = 400, CELL = SIZE / GRID
let ctx, snake, dir, nextDir, food, speed, timer = null
```

- 蛇/方向/食物/计时器**全是模块级单例变量** → 双人需要一份"状态对象"装两条蛇
- `timer = setInterval(tick, speed)`，而 `speed` 会随吃食物变快 → **两个人的速度被同一个定时器绑死**
- `placeFood()` 用 `Math.random()` → 两端各自随机必然不同步
- 输入 `onKey` 直接改 `nextDir` → 联机要变成"本地立即响应 + 同步给对手"
- Game.vue 一个文件 936 行，模板/脚本/样式全在一起

## 2. 三种同步模型，为什么选"房主权威"

| | A. 服务端权威 | B. 房主权威（推荐） | C. 帧同步 / 锁步 |
|---|---|---|---|
| 谁跑游戏规则 | Java 重写一遍 | **玩家 1 的浏览器** | 两端各跑一遍 |
| 后端工作量 | 大（房间 + 全套规则 + 定时器） | **小（纯转发）** | 中（转发 + 帧号对齐） |
| 规则来源 | **两份**（JS 一份、Java 一份） | **一份** | 一份 |
| 网络流量 | 中（快照） | 中（快照） | 最小（只传输入） |
| 断线影响 | 小 | **玩家 1 掉线即整局结束** | 小 |
| 反作弊 | 强 | **无** | 弱 |
| 实现难度 | 高 | **低** | 中高（要求确定性） |

**选 B 的三个理由（都是这个项目特有的）**

1. **规则只留一份**。这个项目的文档反复强调"改地图只动 maps.js""改皮肤只动 skins.js"——
   如果把 `tick()` 用 Java 重写，就变成"改规则要改两个文件、还必须保持完全一致"，
   这是最容易长歪的地方。选 B 就永远不会出现"单人和联机手感不一样"。
2. **不需要重写确定性**。C 方案要求 `Math.random()` 换成带种子的 PRNG、
   `setInterval` 换成固定步长，还要处理输入延迟对齐——对一个练手项目来说收益不划算。
3. **后端退化成"聊天室"**。核心只有"按房间号把 A 的消息转给 B"，
   一个 `ConcurrentHashMap<String, Room>` 就够了，不用引入 Redis、定时器池、序列化框架。

**代价（要认下来）**：房主有天然的"本地零延迟"优势、房主掉线即整局结束、没有反作弊。
这三点对"两个人图个乐"的目标完全可接受。将来若要防作弊或做 4 人以上，再升级到 A —— 
架构上预留了路径（见第 4.3 节）。

## 3. MVP 架构（B 方案）

```
┌──────────────┐        WebSocket（同一个 8080）        ┌──────────────┐
│  玩家1 浏览器  │  ── 输入 + 每 tick 的权威快照 ──▶       │  玩家2 浏览器  │
│  · 跑游戏规则  │                                      │  · 只渲染      │
│  · 房主/权威   │  ◀── 输入（方向、ready）──────────     │  · 本地预表现  │
└──────┬───────┘                                      └──────┬───────┘
       │                                                     │
       └────────────► Spring Boot :8080 ◄───────────────────┘
                     · RoomController（HTTP：创建/加入/查询）
                     · RoomWebSocketHandler（WS：纯转发 + 心跳 + 掉线通知）
                     · RoomService（内存房间表 + TTL 清理）
                     · 不含任何游戏规则
```

### 3.1 一局的生命周期

```
创建房间(HTTP) ─▶ 等待对手(WS 订阅房间) ─▶ 双方 ready ─▶ 3-2-1 倒计时(房主发 at 时间戳)
   ─▶ 游戏中(房主 15Hz 广播快照，玩家2 插值渲染) ─▶ 有人死 ─▶ 结算(胜/负/平)
   ─▶ 「再来一局」复用同一房间（不重新建）｜房间空闲 5 分钟自动回收
```

### 3.2 为什么用"快照广播"而不是"只传输入"

MVP 阶段选快照，是因为它**天然不会不同步**：玩家 2 看到的一切都以房主为准，
没有"两个人各算各的、算岔了"的可能（desync 是联机最难查的一类 bug）。

一帧快照大致长这样（只是一个方向，最终字段待定）：

```json
{ "t": "state", "tick": 128,
  "food": { "x": 7, "y": 3 },
  "snakes": [
    { "p": "p1", "body": [[10,10],[9,10],[8,10]], "dir": "R", "alive": true, "score": 30, "skin": "classic" },
    { "p": "p2", "body": [[5,5],[5,6],[5,7]],      "dir": "U", "alive": true, "score": 20, "skin": "neon" }
  ] }
```

15Hz × 上面这种小 JSON，一局几分钟是**几 MB 级别**，本机/局域网毫无压力。

## 4. 双人规则必须先定的几件事（我的建议值）

这些是"产品规则"，不是技术问题，但**不定清楚就没法动手**。

| # | 问题 | 建议默认值 | 理由 |
|---|---|---|---|
| 1 | 食物共享还是各吃各的 | **共享一个食物**，谁先吃到谁加分 | 有争夺感，才叫联机；各吃各的只是两条单人在同一屏 |
| 2 | 撞到对方身体怎么办 | **撞者死**（对方无事） | 简单、可预期；"互撞双死"可在 P1 作为可选项 |
| 3 | 头对头相撞 | **双方都死 → 平局** | 最公平，也最容易解释 |
| 4 | 速度递增怎么算 | **各自按自己的长度**决定步进间隔 | 必须改掉现在的"全局一个 timer"（见 8.3） |
| 5 | 分值 | 沿用地图分值（10/15/12） | 不动现有 config |
| 6 | 胜负判定 | 分高者胜；同分则蛇长者胜；再同则平 | 需要一条明确的规则，否则结算页没法写 |
| 7 | 地图怎么选 | 房主选，进房后同步给对手 | P1 再考虑"双方投票" |
| 8 | 皮肤 | **各选各的** | 复用 skins.js，几乎免费，体验提升明显 |
| 9 | 是否需要登录 | **不需要**，用户名可选（沿用 sessionStorage） | 和现有 `/api/record/*` 的"userId/username 至少传一个"精神一致，但房间本身不强制 |
| 10 | 这一局算不算进排行榜 | **MVP 不算**（见第 7 节） | 双人局含互相干扰，混进单人榜会毁掉榜单含义 |

## 5. 后端设计（新增，约 3 个类）

### 5.1 依赖

```xml
<!-- pom.xml 加一行；.m2 里已有 3.4.5，离线可用（已核实 jar 存在） -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-websocket</artifactId>
</dependency>
```

### 5.2 类职责

| 类 | 职责 | 备注 |
|---|---|---|
| `RoomController` | HTTP：`POST /api/room/create`、`POST /api/room/join`、`GET /api/room/{code}` | 沿用 `Result{code,msg,data}` |
| `RoomService` | 内存房间表 `ConcurrentHashMap<String, Room>`；建房/加入/离开/TTL 回收/心跳 | 房间号 4~6 位大写字母数字，避免易混字符 |
| `RoomWebSocketHandler` | `TextWebSocketHandler`：按房间号转发消息、掉线广播 `peer-left`、心跳 `ping/pong` | **不含任何游戏规则** |
| `WebSocketConfig` | `@EnableWebSocket` 注册 handler，路径 `/ws/room` | |

**房间里存什么**：`code`、`mapId`、`players[2]`（每个含 `session`、`username`、`ready`、`role=host/guest`）、`createdAt`、`lastActiveAt`。
**不存**：任何游戏状态（那是房主浏览器的事）。

### 5.3 消息协议（草案）

客户端 → 服务端：

| 消息 | 载荷 | 说明 |
|---|---|---|
| `join` | `{room, username}` | 进房；第二个进来的人自动成为 guest |
| `ready` | `{ready}` | 准备好了没 |
| `input` | `{dir, seq}` | 方向输入（转发给房主） |
| `state` | `{tick, food, snakes}` | **房主专用**，权威快照 |
| `over` | `{winner, scores}` | 结算，房主发 |

服务端 → 客户端：

| 消息 | 载荷 | 说明 |
|---|---|---|
| `room` | `{code, mapId, players:[...]}` | 房间状态（进人/退人时广播） |
| `start` | `{seed, mapId, at}` | 双方就绪，房主发 `at` 时间戳让两端对齐倒计时 |
| `peer-left` | `{username}` | 对手掉线 |
| `error` | `{msg}` | 房间不存在 / 房间满 |

> 心跳：客户端 10 秒一次 `ping`，服务端 30 秒没收到就判定掉线并广播 `peer-left`。
> **不要**依赖 TCP 自己发现断线（拔网线/休眠时可能很久才发现）。

### 5.4 前端必须先改的一处配置

```js
// frontend/vite.config.js —— 现在只有 http 代理，WebSocket 不会走代理
'/api': { target: 'http://localhost:8080', changeOrigin: true }
// 需要补（否则 ws 直连 8080，容易踩跨域/端口不一致的坑）
'/ws':  { target: 'ws://localhost:8080', ws: true, changeOrigin: true }
```

## 7. 数据库与排行榜：建议 MVP 不入库

现有 `game_record` 是**一人一条**的流水（`user_id` / `username` / `score` / `map_id` …），
双人一局要落两个玩家的数据，会遇到三个选择：

| 方案 | 做法 | 评价 |
|---|---|---|
| **X（推荐 MVP）** | 双人局**不入库**，纯娱乐 | 零改动、零风险。缺点：玩完没痕迹 |
| Y | 一局结束后**双方各写一条 `game_record`** | 复用现有接口，但要解决"对手是谁"没字段可放的问题（现有字段都不合适） |
| Z | 新建 `game_match` 表（双方 id、比分、胜者） | 最干净，但要动 `schema.sql`，且这台机器每次开机重置，表结构变更要额外小心 |

**排行榜更要想清楚**：现在 `/api/user/score` 的语义是"历史最高分"，
双人局里对手会挡路、也可能互相干扰，**混进同一个榜会让榜单失去可比性**。
建议：要么不入榜，要么在 `user` 表加个独立字段（如 `vs_score`）另开一个榜。

## 8. 风险与坑（每一条都对着这个项目的实际情况）

1. **离线构建**：已核实 `.m2` 里有 `spring-boot-starter-websocket-3.4.5.jar`、
   `spring-websocket-6.2.6.jar`、`tomcat-embed-websocket` → **不会破坏离线优先**。
   （若哪天换到别的框架版本，这条要重新核。）
2. **vite 代理没配 ws**：`/api` 那条代理管不了 WebSocket，必须单独加 `ws: true`，
   否则会出现"HTTP 接口全通、WS 连不上"这种很难一眼看出的故障。
3. **`setInterval(tick, speed)` 的速度耦合**：现在蛇变长 → `speed` 变小 → 重新
   `setInterval`。双人时这会变成"一个人吃快了，另一个人的节奏也被改"。
   必须改成**固定 tick（如 60ms）+ 每条蛇各自累计步进**。
4. **`Math.random()` 造食物**：联机必须由权威端生成食物并通过快照下发
   （或者用种子 PRNG），否则两端食物位置必然不同。
5. **Game.vue 936 行**：直接往里塞联机逻辑 = 不可维护。
   必须先抽 engine（第 6.1 节），这是整个任务里最大的一块工程。
6. **这台机器每次开机重置**：房间状态只放内存是**正确**的（不要试图持久化房间）；
   但也要接受"重启即所有房间消失"。
7. **单人模式回归**：抽 engine 之后，单人玩法、时长统计（要扣暂停）、
   回放轨迹编码（`encodeTrack`）、"超过最高分才写库"这些行为**必须逐项复验**，
   否则联机功能做完，单人坏了——这是最典型的得不偿失。
8. **无鉴权**：登录态只在 `sessionStorage`，房间码可被猜 → 明确"内网/本机 demo"定位，
   别当成能公网跑的东西。
9. **`SERVER__PORT` 环境变量**：新加的 WS 路径同样在 8080 上，沿用现有规避方式即可，
   不要另外开端口（一开就要动 `_env.cmd`、防火墙、代理三处）。

## 9. 分阶段实施计划

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0 最小可玩** | 抽 engine（单人行为不变）→ 房间码建房/加入 → WS 转发 → 房主权威快照 → 两蛇同图 → 胜负结算 → 掉线提示 | 两台浏览器各开一个座位，能完整打完一局并看到胜负 |
| **P1 体验** | 双方各选皮肤、地图同步、再来一局、倒计时对齐、对手位置插值、大厅显示在线房间数 | 连续玩 5 局不用刷新页面 |
| **P2 打磨** | 双蛇回放（复用 replay.js）、可选"互撞双死"、观战、快速匹配、服务端权威（反作弊） | —— |

**建议只先做 P0 的一半**：先把 `engine.js` 抽出来并让单人模式跑通，
这一步做完就能确认"联机的可行性地基"是稳的，再决定要不要继续。

## 10. 怎么验证（沿用这次首页功能用过的那套办法）

1. **断线/并发用脚本模拟**：写个 python 脚本开两个 WebSocket 客户端，
   一个当房主发快照、一个当玩家收，跑 200 个 tick 校验状态一致、顺序不乱、掉线能广播。
   （比开两个浏览器快得多，也更容易复现边界）
2. **两个真实浏览器**：无头 Chrome 用**两个不同的 `--user-data-dir`** 各开一个页面，
   分别截图对比——两条蛇的位置在两屏上必须一致。
3. **回归单人**：改造 engine 前后，各打一局，比对分数、蛇长、时长、回放步数是否一致。
4. **房间边界**：房间不存在、房间满、重复加入、房主秒退、双方同时死 —— 逐个过一遍。

## 11. 需要你拍板的问题

1. 采用 **B（房主权威）** 这个方向吗？还是你更想要 A（服务端权威，能反作弊但要重写规则）？
2. 对战规则按第 4 节那 10 条默认值走吗？特别是 **撞对方身体 = 撞者死** 和 **平局判定**。
3. 双人局 **要不要入库 / 要不要上榜**？（我建议 MVP 都不）
4. 房间形态：**房间码邀请**（简单、可控）还是也要**快速匹配**（要多一个排队队列）？
5. 先做 P0，还是**只先把 engine.js 抽出来**（把地基验证了再谈联机）？

> 我的建议是 **第 5 问选后者**：先抽 engine，单人行为零变化，再上联机。
> 这样万一联机方向有变，抽出来的 engine 也不亏——它对单机模式本身也是纯收益。
